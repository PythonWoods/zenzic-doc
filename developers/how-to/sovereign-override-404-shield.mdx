# The Sovereign Override: ZENZIC_EXTRA_ARGS and the Environmental Invariant

This guide explains when to use `ZENZIC_EXTRA_ARGS` for runtime CI constraints versus
`excluded_external_urls` in `.zenzic.toml` for permanent infrastructure exclusions — and
why the distinction matters for the clone-and-run parity contract.

---

## The Environmental Invariant (ZRT-010)

In the Zenzic ecosystem, we strictly enforce **Clone & Run Parity (ZRT-010)**. A developer
running `just verify` locally must experience the exact same pass/fail outcome as the CI
runner — not because the environments are identical, but because environmental differences
must never alter the *quality verdict*.

`ZENZIC_EXTRA_ARGS` exists to describe constraints imposed by the host machine, not to
adjust quality policy. Examples of legitimate host constraints:

- The CI runner operates behind a firewall and cannot reach external URLs (`--no-external`).
- The security pipeline requires SARIF output for ingestion into a vulnerability tracker
  (`--format sarif`).
- A shared runner has limited CPU and needs concurrency tuned down (`--workers 2`).

None of these change whether the documentation is correct. A developer on an unrestricted
workstation omits these flags, verifies the same docs, and arrives at the same pass/fail.
That is the invariant.

:::danger What ZRT-010 prohibits
Using `ZENZIC_EXTRA_ARGS` to suppress a failing URL because it does not exist yet, or
to hide a structural problem that the local developer would catch. That breaks parity: CI
would pass while the local run fails (or vice versa), making the score non-deterministic.
:::

## Two-Tier Exclusion System

Zenzic intentionally separates two kinds of exclusions:

| Layer | Mechanism | Committed to repo | Who controls it |
| :--- | :--- | :---: | :--- |
| **Content & infrastructure policy** | `excluded_external_urls` in `.zenzic.toml` | ✅ Yes | Repo maintainer |
| **Runtime environmental constraint** | `ZENZIC_EXTRA_ARGS` in CI secret | ❌ No | CI operator |

The `.zenzic.toml` layer is the project's long-term, reviewable statement: *"These URLs are
excluded for documented structural reasons."* The `ZENZIC_EXTRA_ARGS` layer is ephemeral
machine configuration that must not carry policy.

---

## Decision Matrix

Use the following table to decide which mechanism applies:

| Scenario | Correct mechanism | Rationale |
| :--- | :--- | :--- |
| GitHub repo URL returns HTTP 429 (rate-limited) from CI | `.zenzic.toml` `excluded_external_urls` | Permanent structural constraint; developer on unrestricted network would also skip it |
| Third-party service consistently times out (> 10 s) in all environments | `.zenzic.toml` `excluded_external_urls` | Infrastructure reality, not a transient state |
| URL for an unreleased page (exists in release branch, not on main yet) | `ZENZIC_EXTRA_ARGS --exclude-url` | Transient; must be removed post-deploy |
| CI runner behind firewall, cannot reach any external URL | `ZENZIC_EXTRA_ARGS --no-external` | Host constraint; local developer is not behind the firewall |
| SARIF output required for security pipeline | `ZENZIC_EXTRA_ARGS --format sarif` | Output format; no quality impact |
| Concurrency tuning for shared runner | `ZENZIC_EXTRA_ARGS --workers N` | Resource constraint; no quality impact |

## Approved Use Cases for ZENZIC_EXTRA_ARGS

### Network Isolation

When the CI runner cannot reach external URLs (air-gapped or firewall-restricted network):

```yaml
# .github/workflows/audit.yml
env:
  ZENZIC_EXTRA_ARGS: "--no-external"
```

Or to exclude a specific transient URL while keeping all other external checks active:

```yaml
env:
  ZENZIC_EXTRA_ARGS: "--exclude-url https://example.com/prelaunch-page"
```

### Security Reporting (SARIF)

When the pipeline ingests SARIF findings into GitHub Advanced Security or a vulnerability tracker:

```yaml
env:
  ZENZIC_EXTRA_ARGS: "--format sarif --output zenzic.sarif"
```

Upload the artifact after the audit step completes.

### Concurrency Tuning

When the runner is resource-constrained and the default worker pool saturates the CPU:

```yaml
env:
  ZENZIC_EXTRA_ARGS: "--workers 2"
```

Values above the default (4) are also valid when the runner has excess capacity.

## 404 Emergency Protocol

If Zenzic fails on a pre-launch external URL (HTTP 404), apply a surgical runtime exclusion:

```bash
# Local verification with a transient exclusion
ZENZIC_EXTRA_ARGS="--exclude-url https://example.com/prelaunch" just verify
```

In CI, store the exclusion as a secret (`secrets.ZENZIC_EXTRA_ARGS`) and inject it
via `env:` — never hard-code it in the workflow YAML.

**Lifecycle rules for every ZENZIC_EXTRA_ARGS exclusion:**

1. Exclude only the exact pre-launch URL(s). Never exclude broad domains without explicit
   maintainer approval.
2. Add a `# TODO: Remove post-deploy <version>` comment in the workflow or secret
   description so the exclusion has a named removal trigger.
3. Remove the exclusion within one release cycle of the URL becoming publicly reachable.

## .zenzic.toml Exclusion Pattern

When a structural constraint is permanent enough to commit, document the rationale inline:

```toml
[external_links]
excluded_external_urls = [
    # GitHub repo URLs return 429 (rate-limited) in CI — structural constraint, not transient.
    "https://github.com/example/repo",
    # Facebook debugger consistently times out (> 10 s) from CI environments.
    "https://developers.facebook.com/tools/debug/",
]
```

Each entry must have a comment explaining why it is excluded. Uncommented entries will be
flagged in code review.
