# Docusaurus Adapter Architecture

The `DocusaurusAdapter` is responsible for translating the physical filesystem state of a Docusaurus project into Zenzic's universal Virtual Site Map (VSM). Because Docusaurus is a Node.js React framework, Zenzic must emulate its routing logic entirely in Python using static analysis.

## The Emulation Contract

Zenzic does not execute `docusaurus build` or evaluate JavaScript. Instead, it parses `docusaurus.config.ts` (or `.js`) statically to extract the plugin configurations. This allows Zenzic to accurately predict the final URLs generated by the Docusaurus build pipeline.

### Route Resolution Semantics

Docusaurus generates routes based on a combination of filesystem paths and plugin configuration. Zenzic emulates this using the following rules:

1. **Frontmatter Overrides (`slug`)**: Docusaurus allows authors to override the default filesystem-based route using the `slug` frontmatter field. Zenzic respects this:
   - **Absolute Slugs**: If a slug begins with a `/` (e.g., `slug: /custom`), Docusaurus prepends the plugin's `routeBasePath`. Zenzic correctly prepends the `routeBasePath` to absolute slugs to prevent false-positive orphaned pages.
   - **Relative Slugs**: If a slug is relative (e.g., `slug: custom`), it replaces the last segment of the filesystem path.

2. **Blog Date Extraction**: Docusaurus blog posts often use a filename convention like `YYYY-MM-DD-slug.md`. When generating the URL, Docusaurus extracts the date into path segments (`/YYYY/MM/DD/slug/`). Zenzic natively parses these filenames using regular expressions to emulate the exact URL generation logic, ensuring that blog posts with dates are mapped correctly into the VSM.

3. **File-Based Linking**: Zenzic resolves physical file links exactly as Docusaurus does. Zenzic natively understands Docusaurus's **Root-Relative Magic**—if a physical file link (e.g., `guides/install.mdx`) lacks a relative (`./` or `../`) or absolute (`/`) prefix, Zenzic gracefully falls back to resolving the path relative to the active plugin root (e.g., the `docs/` or `blog/` folder). You do not need to alter valid Docusaurus links.

This architectural approach allows Zenzic to provide zero-false-positive link validation and orphan detection without the overhead of a Node.js runtime or dynamic execution.

## The Data Contract for Dynamic Routing

Zenzic enforces absolute determinism through a pure Python static analysis architecture. Consequently, it does not execute JavaScript or TypeScript.

To resolve Docusaurus-specific routing without violating the Zero Subprocess mandate, Zenzic establishes a strict **Data Contract**:

### 1. Webpack `@site` Aliases
Zenzic statically intercepts and strips the `@site/` alias during path resolution. Links utilizing this alias are correctly re-mapped to the physical repository root exactly as Webpack would at runtime. You do not need to alter valid Docusaurus links.

### 2. Generated Category Indices
Docusaurus sidebars dynamically generate virtual `/category/` routes at runtime. Since Zenzic cannot execute TypeScript to discover these virtual routes, you must use **`sidebars.json`** (or YAML) instead of `sidebars.ts`.

When Zenzic detects `sidebars.json` in the Docusaurus root, it automatically parses the file to harvest any `generated-index` routes and maps them accurately into the Virtual Site Map.

> **Data Contract:** To allow Zenzic to validate generated category indices, you must use `sidebars.json` instead of `sidebars.ts`. If you choose to use TypeScript for sidebars, you must accept a static blindspot for generated indices.

### Fallback: Suppressing Dynamic Categories

If you must use `sidebars.js` or `sidebars.ts` for dynamic logic, Zenzic will be statically blind to generated indices. To prevent Z104 false positives on these links, you can suppress the errors using the following snippet in your `.zenzic.toml`:

```toml
[governance.directory_policies]
# Silence Z104 on links pointing to JS-generated category indices
"docs/category/**" = ["Z101", "Z104"]
```

### Ontological Boundaries: React and MDX

Zenzic validates static Markdown. It does not execute React or bundle MDX. Zenzic parses files in isolation and uses a pure-Python AST parser to build the Virtual Site Map. Because of this architectural purity, there are two distinct boundaries where Zenzic will statically fail to find anchors:

1. **React-generated IDs**: If an `id` is generated dynamically by a React component (e.g., `<APITable id={name} />`), Zenzic's AST parser cannot see it.
2. **Imported MDX Partials**: If an anchor is defined inside an imported MDX partial, Zenzic will not aggregate it into the parent file's namespace.

`Z102` errors targeting React-generated IDs or imported MDX partials are expected. You should explicitly suppress these errors via your `.zenzic.local.toml` configuration or using an inline `zenzic:ignore` comment. This is a structural fact of static analysis and guarantees Zenzic's mathematically determinism without the overhead of a JavaScript runtime.
