# Finding Codes Reference

Every issue detected by Zenzic is tagged with a **canonical finding code** (`Zxxx`). This encyclopedia provides the technical context and practical remediation steps for every diagnostic signal.

## Tier Model (ADR-012)

Zenzic organizes diagnostics into four operational tiers:

| Tier | Ownership | Format | Scope |
|---|---|---|---|
| Core | Zenzic | `Zxxx` | Built-in scanners and system findings |
| Governance | Zenzic | `Z6xx` | Opt-in policy checks (`[governance]`) |
| Plugin | Third-party | `<plugin-id>:<code>` | External entry-point rules |
| Custom | Project local | `ZZxxx` | `[[custom_rules]]` declared in TOML |

## Stability Contract

The code registry is governed by immutable contract surfaces:

- `FROZEN_CODES`: codes that cannot be renumbered or semantically changed without architecture-level approval.
- `NON_SUPPRESSIBLE_CODES`: security codes that cannot be silenced inline.
- `PLUGIN_FORBIDDEN_EXITS`: plugins are forbidden from emitting Exit 2/3 (reserved for core security semantics).

:::tip[Deep-linking]
Each code has a permanent anchor. You can link directly to a specific code using `https://zenzic.dev/docs/reference/finding-codes#z101`.
:::

## Category Overview

Zenzic organizes findings into **eight diagnostic categories**, each addressing a specific pillar of documentation integrity:

| **Category** | **Range** | **Purpose** | **Default Severity** | **Suppressible?** |
|---|---|---|---|---|
| **Z0xx** | Migration & Compatibility | Engine deprecation; migration guidance | `error` | ❌ No (fatal abort) |
| **Z1xx** | Link Integrity | Broken, empty, circular links; orphaned pages; path issues | `error`/`warning`/`info` | ✅ Yes |
| **Z2xx** | Security (credential scanner) | Secret detection; path traversal; security incidents | `warning`/`security_breach`/`security_incident` | 🔒 **Never** |
| **Z3xx** | Reference Integrity | Dangling/duplicate reference definitions | `error`/`warning` | ✅ Yes |
| **Z4xx** | Structure | Directory indexes, orphan pages, missing alt text, config assets | `info`/`warning` | ✅ Yes |
| **Z5xx** | Content Quality | Placeholder text, short content, snippet validation, regressions | `warning`/`error` | ✅ Yes |
| **Z6xx** | Governance | Brand obsolescence, translation parity (opt-in) | `warning` | ✅ Yes |
| **Z9xx** | Engine & System | Rule execution errors, timeouts, system-level diagnostics | `error`/`warning` | ✅ Yes |

:::info[Per-line suppression syntax]
Suppress a finding on a specific line with a format-aware comment on that same line.\
**Markdown (.md):** `<!-- zenzic:ignore: Zxxx -->`\
**MDX (.mdx):** `{/* zenzic:ignore: Zxxx */}`\
See [Suppression Policy](./suppression-policy.mdx) for the full reference including interaction with `--strict` mode.
:::

### Exit Code Contract

Zenzic uses exit codes to communicate severity across CI/CD pipelines:

* **Exit 0:** All checks passed (or suppressed via `--exit-zero`).
* **Exit 1:** Errors and warnings detected; use `--strict` to promote warnings.
* **Exit 2:** Security breaches (Z201 CREDENTIAL_SECRET) or policy violations (Z204 FORBIDDEN_TERM). **Never** suppressed.
* **Exit 3:** Security incidents detected (Z203 PATH_TRAVERSAL_FATAL). **Never** suppressed, even with `--exit-zero`.

## Z0xx — Migration & Compatibility

### Z000: UNSUPPORTED_ENGINE {#z000}

* **Severity:** `error` (Fatal — aborts execution immediately)
* **Technical Context:** Z000 is a **fatal configuration error**, not a collectable finding. It surfaces as a `ConfigurationError` exception when the adapter factory encounters a deprecated or removed legacy engine alias in `.zenzic.toml`. Execution stops before any scan begins; Z000 will **not** appear in `--format json` output or the findings array.
* **Architectural Rationale:** A deprecated engine alias does not merely cause a misconfiguration — it invalidates the determinism of the Virtual Site Map. Zenzic's core guarantee is `score(repo) == score(repo)` across any environment. If the adapter factory accepted an unknown engine and continued with a fallback heuristic, the VSM produced would be non-deterministic: different environments might resolve different adapters, produce different route tables, and generate different scores for identical input. Hard abort is the only response that preserves the determinism contract.
* **Remediation Steps:**
    1. Open your `.zenzic.toml` or `pyproject.toml`.
    2. Locate the `engine` field.
    3. Set `engine = "standalone"`.
    4. If you are using MkDocs, ensure it is set to `engine = "mkdocs"`.

## Z1xx — Link Integrity

### Z101: LINK_BROKEN {#z101}

:::info[Quality Score — Structural tier (30%) | −8.0 pts / occurrence]
Z101 counts toward the **Structural** tier of the [Deterministic Quality Score](./scoring-algorithm.mdx). Penalty: **−8.0 pts per occurrence**, capped at 30 pts for the tier.
:::

* **Severity:** `error`
* **Technical Context:** Emitted during Pass 2 (Validation) of the Two-Pass Engine. A relative link points to a resource that does not exist within the **Virtual Site Map (VSM)**. This means that while the file might exist physically, it is either outside the docs scan scope or was excluded by an exclusion rule.
* **Architectural Rationale:** A broken link is the silent rupture of a bidirectional contract between author and reader. The author committed a path; every reader trusts that path leads somewhere. When a file is renamed or deleted, standard CI pipelines do not surface the break — the build succeeds, the test suite passes, and the damage propagates invisibly until a user hits the 404. Zenzic catches this break before any build runs, making it the only gate in the pipeline that can intercept this class of documentation rot at the source.
* **Remediation Steps:**
    1. Verify the physical existence of the target file.
    2. Check the relative path calculation (e.g., `../folder/target.md`).
    3. Ensure the file is not matched by `ignored_patterns` in your config.
    4. If referencing a file outside `docs/`, use a global path or symlink (though relative is preferred).

<ZenzicOutput
  status="error"
  code="Z101"
  exitCode={1}
  compact
  rows={[{ code: 'Z101', file: 'docs/guides/setup.md:14', message: "Broken link → 'install.md' (target not found)", severity: 'error' }]}
/>

:::note[Architectural Boundary — Cross-Page Fragment Validation]
Zenzic validates the existence of the **route** a link points to. It does not validate the specific fragment (`#heading`) within a different page. If a link such as `/docs/reference/cli#specific-heading` points to a valid route, Zenzic emits no finding even if `#specific-heading` does not exist on that page.

For same-page anchor links (links of the form `#section-on-this-page`), see [Z102: ANCHOR_MISSING](#z102).

For cross-page fragment validation — verifying that `#heading` exists within another page — the static site generator (e.g., Docusaurus) performs this check at build time. Running `npm run build` will surface broken cross-page anchors that fall outside Zenzic's route-graph scope.
:::

### Z102: ANCHOR_MISSING {#z102}

:::info[Quality Score — Structural tier (30%) | −5.0 pts / occurrence]
Z102 counts toward the **Structural** tier of the [Deterministic Quality Score](./scoring-algorithm.mdx). Penalty: **−5.0 pts per occurrence**, capped at 30 pts for the tier.
:::

* **Severity:** `error`
* **Technical Context:** The file target is valid (Z101 pass), but the specific HTML anchor (e.g., `#setup`) cannot be found in the target's header registry. Zenzic parses all Markdown headers and explicit `<a id="...">` tags to build this registry during Pass 1.
* **Architectural Rationale:** A heading is a public contract. When an author writes `## Setup` or declares `{#my-anchor}`, they commit that identifier to every incoming link that references it. When the heading text is edited or the explicit ID removed, the contract breaks silently: the file still exists (Z101 does not fire), but the section the reader expected is gone. Z102 enforces anchor-level contract stability — which a file-existence check alone cannot provide — catching regressions introduced by ordinary heading renames.
* **Remediation Steps:**
    1. Open the target file and verify the heading text.
    2. Ensure the anchor matches the engine-specific slugification (e.g., Docusaurus uses Kebab-case).
    3. If using custom IDs, ensure the syntax `{#id}` or `<a id="id"></a>` is correct.

### Z103: ORPHAN_LINK {#z103}

:::note[Quality Score — No DQS impact (0.0 pts)]
Z103 does **not** reduce the [Deterministic Quality Score](./scoring-algorithm.mdx). It causes exit 1 in standard mode. See [Scoring Algorithm](./scoring-algorithm.mdx) for the complete penalty table.
:::

* **Severity:** `error`
* **Technical Context:** This link points to a file that is present in the VSM but is not included in the site's navigation structure (sidebar/nav). Users may be able to link to it, but they cannot find it via the UI.
* **Architectural Rationale:** A navigation-orphaned page exists in the build but not in the Knowledge Graph that readers traverse. It is reachable only by direct URL — the reader must already know the URL to find it. Such a page has zero discoverability: it cannot be found by following any navigation path, sidebar entry, or documentation tree. Z103 makes this invisibility explicit, giving the author the choice to either add the page to navigation (making it discoverable) or acknowledge intentionally that it is a hidden endpoint.
* **Remediation Steps:**
    1. Add the file to your `mkdocs.yml` navigation or Docusaurus `sidebars.ts`.
    2. If the page is intentional (e.g., a hidden landing page), you can suppress this warning using a `<!-- zenzic-disable Z103 -->` comment.

### Z104: FILE_NOT_FOUND {#z104}

:::info[Quality Score — Structural tier (30%) | −8.0 pts / occurrence]
Z104 counts toward the **Structural** tier of the [Deterministic Quality Score](./scoring-algorithm.mdx). Penalty: **−8.0 pts per occurrence**, capped at 30 pts for the tier.
:::

* **Severity:** `error`
* **Technical Context:** A low-level filesystem error. The engine attempted to open a file referenced by a link or asset but received a `FileNotFoundError`. This typically happens when a file is moved or deleted during a concurrent build process.

  **Slug-mismatch variant (Docusaurus):** Z104 also fires when an absolute link targets a project-owned route prefix (e.g. `/blog/`) that is scanned by Zenzic, but the exact slug does not exist in the Virtual Site Map. The most common cause is a `slug:` field in frontmatter that differs from the URL used in a link:

  ```mdx title="blog/2026-05-05-release-log.mdx"
  {/* This link is wrong — the real slug is zenzic-v070-release */}
  [Read the previous post](/blog/zenzic-v070)
  ```

  ```yaml title="blog/2026-04-29-zenzic-v070-release.mdx (frontmatter)"
  slug: zenzic-v070-release
  ```

  Zenzic output:

  ```
  blog/2026-05-05-release-log.mdx:12: '/blog/zenzic-v070' not found in the site map
  💡 Did you mean: '/blog/zenzic-v070-release/'?
  ```

  The Virtual Site Map is built from frontmatter slugs (not physical filenames), so the physical file `2026-04-29-zenzic-v070-release.mdx` does not create the route `/blog/zenzic-v070/` — only `/blog/zenzic-v070-release/`.

* **Architectural Rationale:** The slug-mismatch variant reveals a structural property unique to Docusaurus: the `slug:` frontmatter field decouples a file's public URL from its physical path. This decoupling makes URL-based links non-portable — a link to `/blog/my-post/` can break invisibly if the target file's `slug:` is changed, even though the file itself still exists on disk and no Z101 fires. Zenzic's Virtual Site Map builds routes from frontmatter slugs, not filenames, making this class of silent slug-mismatch break detectable before the build runs.
* **Remediation Steps:**
    1. Ensure no other process is modifying the `docs/` directory during the Zenzic scan.
    2. Verify that your `docs_dir` setting is correct and that the file path is absolute relative to the repository root.
    3. *(Slug-mismatch variant)* Run `zenzic inspect routes --kind physical` to see all canonical URLs in the VSM, and update the link to match the exact slug declared in the target file's frontmatter.

### Z105: ABSOLUTE_PATH {#z105}

:::info[Quality Score — Structural tier (30%) | −2.0 pts / occurrence]
Z105 counts toward the **Structural** tier of the [Deterministic Quality Score](./scoring-algorithm.mdx). Penalty: **−2.0 pts per occurrence**, capped at 30 pts for the tier.
:::

* **Severity:** `error`
* **Technical Context:** Absolute paths (e.g., `C:\Docs\page.md` or `/home/user/docs/page.md`) break documentation portability. Zenzic flags these to prevent "It works on my machine" syndrome in CI/CD pipelines.

  **Project-owned prefixes are exempt from Z105 but not from Z104.** Docusaurus sites often use absolute links starting with `/blog/`, `/docs/`, or other `routeBasePath` values to cross plugin boundaries. Zenzic auto-detects these prefixes from the engine configuration (Zero-Config — no `.zenzic.toml` entry required) and suppresses Z105 for them.

  However, suppressing Z105 does not mean the link goes unchecked. For prefixes that are fully scanned (e.g. `blog/` is in scope), Zenzic performs a VSM lookup and raises a [Z104 — FILE_NOT_FOUND](#z104) finding if the exact route is absent. This catches slug mismatches and renamed posts that break absolute links. The lookup cost is $O(1)$ — a single hash-map `get()` — with no measurable impact on scan time.

  | Link | Z105 | VSM check | Outcome |
  | :--- | :---: | :---: | :--- |
  | `/blog/correct-slug` (slug exists in VSM) | ✅ exempt | ✅ passes | No finding |
  | `/blog/wrong-slug` (slug absent from VSM) | ✅ exempt | ❌ fails | **Z104** |
  | `/developers/intro` (sibling plugin content root, page exists) | ✅ exempt | ✅ passes | No finding |
  | `/developers/ghost` (sibling plugin content root, page absent) | ✅ exempt | ❌ fails | **Z104** |
  | `/api/v1/users` (unknown prefix) | ❌ **Z105** | — | Z105 |

* **Architectural Rationale:** An absolute path in documentation source binds the link to a single host's filesystem layout — the polar opposite of the portability contract that documentation must honour. Unlike code, where absolute imports may be acceptable when scoped to a published package, a documentation absolute path leaks the author's machine state into a public artifact: the build will succeed on the author's laptop and fail in CI, in a fork, or on a contributor's environment. Zenzic flags Z105 as a Structural finding because the break is not stylistic — it is a portability defect that compounds silently: every absolute path adds one more environment-specific assumption to the documentation, until a reorganisation, mirror, or migration surfaces them all at once.
* **Remediation Steps:**
    1. Convert the link to a relative path starting from the current file's directory.
    2. Use `@site/` or similar engine-specific aliases if supported (e.g., in Docusaurus).
    3. If you received a **Z104** (not Z105) on an absolute `/blog/` or `/docs/` link, the route prefix is recognised but the slug does not exist — see [Z104 remediation](#z104) above.

### Z106: CIRCULAR_LINK {#z106}

:::note[Quality Score — Informational | 0.0 pts (no DQS impact)]
Z106 is informational only and does **not** reduce the [Deterministic Quality Score](./scoring-algorithm.mdx). Inspect with `--show-info`. See [Scoring Algorithm](./scoring-algorithm.mdx#penalty-table) for the rationale behind the zero-penalty design.
:::

* **Severity:** `info`
* **Technical Context:** Detected by the Graph Integrity module. A set of links forms a directed cycle (A → B → A). This is a structural telemetry signal: it is visible via `--show-info`, excluded from scoring, and does not block the Quality Gate.
* **Remediation Steps:**
    1. Review the content flow to see if one link can be replaced by a broader "See Also" section.
    2. Ensure that users aren't getting trapped between two pages with no clear exit path.

:::note[Architectural rationale]
**Knowledge Graph, not Dependency Graph.** In source code, a dependency cycle (module A imports B, which imports A) is a compilation-time defect. Documentation is a Knowledge Graph: if a Tutorial links a Reference page for technical details, it is expected and desirable that the Reference page links back to the Tutorial as a working example. A densely interconnected graph is a signal of high-quality UX, not a defect.

**Score Anti-Pattern Prevention.** Elevating Z106 to Warning or Error would deduct Quality Score points, pressuring engineers to remove useful links in order to satisfy the linter. This violates the Zero-DBT principle: a linter must only flag genuine defects. An intentional circular link is not a defect to resolve.

**AST Recursion Protection.** The cycle-detection algorithm (iterative DFS, Θ(V+E)) is a mechanical requirement of the Virtual Site Map builder. Identifying cycles mathematically is necessary to interrupt recursion and prevent infinite loops during graph traversal — it is not triggered by a quality concern.

**Topological Telemetry.** `--show-info` exposes Z106 findings as structural metrics, not as violations. An abnormally high cycle density on a single page may indicate an Information Architecture problem worth reviewing — but that evaluation belongs to the engineer, not to the static analyzer.
:::

### Z108: EMPTY_LINK_TEXT {#z108}

:::info[Quality Score — Structural tier (30%) | −1.0 pt / occurrence]
Z108 counts toward the **Structural** tier of the [Deterministic Quality Score](./scoring-algorithm.mdx). Penalty: **−1.0 pt per occurrence**, capped at 30 pts for the tier.
:::

* **Severity:** `error`
* **Technical Context:** Emitted when the visible text in an inline Markdown link or a collapsed reference link is empty or consists only of whitespace. Examples include `[](./page.md)`, `[ ](./page.md)`, and `[][ref]`.
* **Architectural Rationale:** Link text is the machine-readable semantic contract between author and every downstream consumer. Screen readers announce link text as the navigation target description. Search engine crawlers index it as the relationship label between pages. Keyboard navigators rely on it to understand where Tab-focus will lead. An empty or whitespace-only label breaks all three contracts simultaneously: the link exists in the DOM but communicates nothing. Zenzic classifies Z108 as a Structural finding — not a style preference — because it degrades both accessibility and the knowledge graph's semantic layer.
* **Remediation Steps:**
  1. Replace the empty label with descriptive link text, e.g. `[Documentation](./page.md)`.
  2. If the link is only a placeholder, remove it until the destination and label are known.
  3. Re-run `zenzic check links` after the edit to confirm that no Z108 findings remain.

:::tip[Executable Example]
For a hands-on demonstration, create a local fixture containing `[](./target.md)`
and run `zenzic check links` to observe Z108 in isolation.
:::

### Z107: CIRCULAR_ANCHOR {#z107}

:::info[Quality Score — Structural tier (30%) | −1.0 pt / occurrence]
Z107 counts toward the **Structural** tier of the [Deterministic Quality Score](./scoring-algorithm.mdx). Penalty: **−1.0 pt per occurrence**, capped at 30 pts for the tier.
:::

<ZenzicOutput
  status="warning"
  code="Z107"
  exitCode={1}
  compact
  rows={[{
    code: "Z107",
    file: "docs/guide.md",
    line: 42,
    message: "Self-referential anchor link: anchor #intro points to a heading on this very page."
  }]}
/>

* **Severity:** `warning`
* **Technical Context:** Detected by the `CircularAnchorRule` in the pluggable rule engine. A link of the form `[text](#anchor)` where the anchor resolves to a heading on the *same* page is logically circular — it navigates to exactly where the reader already is. The rule slugifies all headings in the file (lowercased, spaces to hyphens, special chars stripped) and matches them against every local anchor link.
* **Architectural Rationale:** A link of the form `[text](#anchor)` where `#anchor` resolves to a heading on the same page is a degenerate cycle of length 1 — it navigates the reader back to the exact position they already occupy. This is distinct from a legitimate table-of-contents link at the top of a page (which links forward to a lower anchor). Z107 fires only when the link and its resolved heading share the same page context: a self-loop that provides zero navigation value and can confuse screen readers and keyboard navigators who expect links to move focus to a different location.
* **Remediation Steps:**
    1. Replace `[text](#anchor)` with plain prose `text` if no navigation is intended.
    2. Or link to the concept on a *different* page that expands it.
    3. If the link is intentional (e.g., a ToC entry at the top of a long page), it is by definition not circular — review the anchor slug match.

## Z2xx — Security (credential scanner)

### Z201: CREDENTIAL_SECRET {#z201}

:::danger[Quality Score — Security Override | FATAL | Exit 2 | Non-suppressible]
Z201 triggers the Security Gate: the [Deterministic Quality Score](./scoring-algorithm.mdx) collapses to **0/100** unconditionally. Exit code **2** (credential leak) — bypasses `--exit-zero`. A documentation source that leaks credentials cannot receive a quality score. See [Scoring Algorithm](./scoring-algorithm.mdx#security-override).
:::

:::danger[🔒 INVIOLABLE — Cannot be suppressed]
`zenzic:ignore: Z201` is **silently rejected**. The credential scanner fires unconditionally on every line. Security findings are facts, not suggestions — a credential leak cannot be declared a false positive.
:::

* **Severity:** `security_breach` (Exit 2)
* **Technical Context:** The credential scanner scans every line — raw and normalised — for known credential patterns. Speculative Base64 decoding is applied to candidate tokens: if decoding reveals a credential pattern, the original (encoded) line is flagged. This prevents obfuscation via Base64 encoding in frontmatter values or code blocks.
* **Architectural Rationale:** Documentation source is untrusted input. It is authored by humans, accepted from external contributors, and processed by CI pipelines that may hold access to production credentials. A single API key committed to a Markdown file — in a rush, before a deadline — is a supply-chain incident, not an editorial mistake: once pushed to a remote, the secret is compromised regardless of any subsequent deletion. Zenzic treats documentation files as code under a security audit, scanning every line unconditionally before any other analysis begins.
* **Remediation Steps:**
    1. **IMMEDIATE:** Rotate the leaked credential. It must be considered compromised.
    2. Remove the secret from the file.
    3. Purge the git history using `git-filter-repo` or a similar tool to ensure the secret is not just hidden but gone.
    4. Use placeholders like `YOUR_API_KEY` for documentation examples.

### Z202: PATH_TRAVERSAL {#z202}

:::danger[Quality Score — Security Override | FATAL | Exit 1 | Non-suppressible]
Z202 triggers the Security Gate: the [Deterministic Quality Score](./scoring-algorithm.mdx) collapses to **0/100** unconditionally. Exit code **1** (standard traversal — distinct from Z203 OS-path incident at Exit 3). The boundary guard cannot be suppressed. See [Scoring Algorithm](./scoring-algorithm.mdx#security-override).
:::

:::danger[🔒 INVIOLABLE — Cannot be suppressed]
`zenzic:ignore: Z202` and `zenzic:ignore: Z203` are **silently rejected**. The path traversal guard enforces the scan boundary unconditionally.
:::

* **Severity:** `error`
* **Technical Context:** A relative path uses `..` segments to escape the `docs/` root boundary. This is a security guardrail to ensure the Zenzic engine does not accidentally disclose or scan sensitive repository files (like `.env` or `config.py`) that aren't part of the documentation.
* **Architectural Rationale:** A path traversal is categorically distinct from a broken link (Z101). A broken link is a maintenance failure; a traversal is a boundary violation. The `docs/` root defines what is public documentation and what is internal infrastructure. A link escaping this perimeter via `..` sequences can expose files that exist in the repository but were never intended for publication. The escape may be accidental (a miscalculated relative path) or deliberate (a template injection probe); Zenzic applies the same Exit 1 to both because the architectural risk — leaking private file paths into rendered documentation — is identical.
* **Remediation Steps:**
    1. Move the target asset or file into the `docs/` or `static/` hierarchy.
    2. If you must reference an external file, use a symbolic link (if permitted) or a literal absolute URL.

### Z203: PATH_TRAVERSAL_FATAL {#z203}

:::danger[Quality Score — Security Override | FATAL | Exit 3 | Non-suppressible]
Z203 triggers the Security Gate at the highest severity: the [Deterministic Quality Score](./scoring-algorithm.mdx) collapses to **0/100** unconditionally. Exit code **3** (OS-path security incident) — the highest exit code in Zenzic, which bypasses `--exit-zero` unconditionally. Distinct from Z202 (Exit 1, generic traversal): Z203 targets system directories (`/etc/`, `/root/`) that signal supply-chain compromise rather than authoring error. See [Scoring Algorithm](./scoring-algorithm.mdx#security-override).
:::

* **Severity:** `security_incident` (Exit 3)
* **Technical Context:** The **path traversal guard** detected an attempt to access restricted OS directories (e.g., `/etc/`, `/root/`). This is treated as a high-authority security incident, triggering a non-zero exit code that cannot be suppressed.
* **Architectural Rationale:** Z203 is structurally distinct from Z202 (generic traversal) in its target class. A path resolving to `/etc/`, `/root/`, `/proc/`, or similar OS directories cannot result from a legitimate documentation workflow — no author constructing documentation links ever targets the system password file. Its presence indicates one of three scenarios: (1) template injection in the documentation build pipeline, (2) a compromised toolchain inserting probe links, or (3) a malicious commit. All three justify Exit 3 (security incident), not Exit 1 (quality error), because they signal a systemic threat to the build environment, not a content authoring mistake.
* **Remediation Steps:**
    1. Investigate the source file for malicious intent or supply-chain compromise.
    2. Remove any absolute paths that reference host-system locations.
    3. Ensure no malicious content is injecting probes into your documentation.

### Z204: FORBIDDEN_TERM {#z204}

:::danger[Quality Score — Security Override | FATAL | Exit 2 | Non-suppressible]
Z204 triggers the Security Gate: the [Deterministic Quality Score](./scoring-algorithm.mdx) collapses to **0/100** unconditionally. Exit code **2** (forbidden-term exposure) — bypasses `--exit-zero`. A documentation source that exposes confidential project terms cannot receive a quality score. See [Scoring Algorithm](./scoring-algorithm.mdx#security-override).
:::

:::danger[🔒 INVIOLABLE — Cannot be suppressed]
`zenzic:ignore: Z204` is **silently rejected**. The Privacy Gate fires unconditionally on every line — a forbidden-term exposure is a security fact, not a suggestion.
:::

:::info[Brand Integrity — Two-Layer Architecture]
Zenzic enforces brand and privacy integrity through two complementary layers:

| Layer | Source | Scope | Severity |
|---|---|---|---|
| **Z204 Privacy Gate** | `forbidden_patterns` in `.zenzic.local.toml` *(git-ignored)* | Private terms — code-names, staging hosts, team aliases | **Exit 2 (Critical)** |
| **Z601 Brand Guard** | `[governance].brand_obsolescence` in `.zenzic.toml` | Deprecated brand terms (e.g. an old product name) | Exit 1 (Quality) |

Use Z204 for secrets you must never commit. Use Z601 for brand hygiene where intentional historical references (e.g. CHANGELOG entries) should be suppressible.
:::

* **Severity:** `security_breach` (Exit 2)
* **Source:** `forbidden_patterns` declared in `.zenzic.local.toml` — the machine-local, git-ignored Enterprise Privacy Gate.
* **Technical Context:** The Privacy Gate performs a case-insensitive verbatim substring scan against every line of every documentation file. Patterns are matched literally — no regex, no wildcards. This makes the guarantee deterministic: if the term is in the file, it will always be found. ### Z111: VIRTUAL_ROUTE_BROKEN {#z111}

* **Severity:** `error` *(reserved)*
* **Technical Context:** A link in your documentation points to a virtual route URL
  (e.g., `/blog/tags/react/`) that was **never generated** because no blog post carries
  that tag value in its `tags:` frontmatter. The route does not exist in the VSM.

  This is distinct from `Z101 LINK_BROKEN` (physical file missing): the URL is
  structurally valid for Docusaurus, but no content source activates it. Zenzic builds
  the Virtual Route map from `md_contents` (files already confirmed to exist on disk),
  so Z111 is strictly a frontmatter/link mismatch — not a file-deletion problem.

  Example: a `docs/index.md` file contains `[React posts](/blog/tags/react/)`, but no
  blog post in `blog/` has `tags: [react]`. Docusaurus will never render that page;
  the link is a 404.

* **Remediation Steps:**
    1. Identify the tag slug in the broken route URL (e.g., `react` from `/blog/tags/react/`).
    2. Search your `blog/` directory for posts whose `tags:` frontmatter should include
       that tag — they may use a capitalised variant (`React`) or a synonym.
    3. Either add the tag to the relevant posts, or update the link to target a tag that
       is actually generated (e.g., `/blog/tags/reactjs/`).
    4. If the link is forward-looking (a tag you plan to introduce), suppress temporarily
       with `{/* zenzic:ignore: Z111 */}` on the offending link.

### Z113: AUTHOR_KEY_COLLISION {#z113}

* **Severity:** `error` *(reserved)*
* **Technical Context:** Two or more Docusaurus `authors.yml` (or `blog/authors/*.yml`)
  files declare the same author key. Docusaurus merges these definitions deterministically
  by priority, but the merge result is silent and fragile — a key collision creates a
  hidden configuration dependency between files that are typically maintained independently.
* **Remediation Steps:**
    1. Search for the colliding author key in all `authors.yml` files under `blog/`.
    2. Decide which definition is canonical and rename the duplicate key.
    3. Update every blog post that uses the renamed key in its `authors:` list.

---

### Z114: LARGE_PAGINATION_SET {#z114}

* **Severity:** `info` *(reserved)*
* **Technical Context:** The blog plugin would generate more than 200 paginated index
  pages (`/blog/page/N/`). Zenzic surfaces this as an informational finding — not a
  blocking error — to prompt a review of the pagination strategy before it becomes a
  navigation UX problem.

  Common causes: a very large number of short blog posts; an extremely low `postsPerPage`
  setting; a date range spanning many years without `archiveBasePath` enabled.

* **Remediation Steps:**
    1. Review `postsPerPage` in your `docusaurus.config.ts` blog block.
    2. Consider enabling the blog archive (`archiveBasePath: 'archive'`) to offload
       historical posts from the paginated index.
    3. Suppress with `{/* zenzic:ignore: Z114 */}` on the link.

## Reserved Codes (Inactive) {#reserved}

The following codes are defined in the Zenzic taxonomy but are **not emitted by the core scanner**. They are documented here for completeness and to prevent accidental re-use of reserved identifiers.

### Z504: QUALITY_REGRESSION {#z504}

* **Severity:** `warning` *(reserved)*
* **Technical Context:** Emitted by `zenzic diff` when the current [Deterministic Quality Score](./scoring-algorithm.mdx) is lower than the saved baseline (`.zenzic-score.json`). Z504 is the signal that bridges the scoring layer and the finding layer — it identifies *which commit introduced a regression*. It is not itself weighted into the score (that would be circular); it is the diagnostic consequence of score degradation.
* **Remediation Steps:**
    1. Run `zenzic score` to see the current score breakdown by category.
    2. Compare with the baseline: identify which category's issue count increased.
    3. Fix the underlying findings (Z101–Z503) that caused the drop.
    4. Run `zenzic score --save` on `main` after the fix to update the baseline.

### Suppressing Diagnostics

Zenzic supports **line-level, per-code suppression** via inline comments. Add a `zenzic:ignore` comment at the end of any line to silence a specific diagnostic for that line only.

**Format-aware suppression (CEO-143 — Polymorphic Suppression Protocol):**

For ``.md`` files use a standard HTML comment (invisible in rendered Markdown):

```markdown
The Obsidian era defined our foundations. <!-- zenzic:ignore: Z601 -->
```

For ``.mdx`` files use a JSX comment (invisible in rendered MDX, safe for Docusaurus/React):

```mdx
The Obsidian era defined our foundations. {/* zenzic:ignore: Z601 */}
```

Each suppression comment silences **only** the specified code on that line. To suppress multiple codes on one line, add multiple comments. To exempt an entire file, use `obsolete_names_exclude_patterns` in `.zenzic.toml` (Z601) or the relevant `excluded_files` patterns.

:::tip[Use suppression sparingly]
Suppression is for intentional, documented decisions — not for silencing findings you haven't reviewed. Every suppressed line should have a corresponding comment or ADR entry explaining why.
:::

### Recommended Workflow

1. **Baseline scan:** Run `zenzic check all` to establish a baseline of findings.
2. **Prioritize security:** Address all Z2xx (credential scanner) findings immediately—these are security-critical.
3. **Fix structural issues:** Resolve Z4xx (Structure) findings to ensure proper navigation and accessibility.
4. **Gradual quality improvement:** Address Z5xx (Content Quality) findings incrementally as part of routine documentation maintenance.
5. **Suppress intentional violations:** Use inline comments sparingly for design decisions (e.g., hidden landing pages, experimental sections).

### Engine-Specific Considerations

* **Docusaurus:** Z103 (ORPHAN_LINK) warnings may be intentional for pages outside the main sidebar. Consider using `sidebars.js` routes or suppressing these findings.
* **MkDocs:** Z401 (MISSING_DIRECTORY_INDEX) is especially relevant in hierarchical docs; ensure every directory has an `index.md`.
* **Standalone Mode:** Orphan detection (Z103, Z402) is disabled without a navigation contract. Use explicitly.

## Integration with CI/CD {#cicd-integration}

For maximum effectiveness, integrate Zenzic checks into your CI/CD pipeline:

```bash
# Fail on any error (Z1xx, Z4xx, Z9xx)
zenzic check all

# Fail on errors OR warnings (promote with --strict)
zenzic check all --strict

# Always exit 0 for non-blocking audits
zenzic check all --exit-zero
```

Use environment-specific configurations to adapt severity:

```toml
[zenzic]
engine = "docusaurus"
strict = false  # Warnings only in dev; use --strict in CI

[[rules]]
code = "Z502"
minimum_words = 50
```
