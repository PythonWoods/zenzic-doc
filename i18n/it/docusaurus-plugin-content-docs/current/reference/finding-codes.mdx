# Riferimento Codici di Finding

Ogni problema rilevato da Zenzic è contrassegnato da un **codice di finding canonico** (`Zxxx`). Questa enciclopedia fornisce il contesto tecnico e i passaggi pratici di rimedio per ogni segnale diagnostico.

## Tier Model (ADR-012)

Zenzic organizza le diagnostiche in quattro tier operativi:

| Tier | Ownership | Formato | Ambito |
|---|---|---|---|
| Core | Zenzic | `Zxxx` | Scanner built-in e finding di sistema |
| Governance | Zenzic | `Z6xx` | Check di policy opt-in (`[governance]`) |
| Plugin | Terze parti | `<plugin-id>:<code>` | Regole esterne via entry-point |
| Custom | Progetto locale | `ZZxxx` | Regole `[[custom_rules]]` nel TOML |

## Stability Contract

Il registro codici è governato da superfici contrattuali immutabili:

- `FROZEN_CODES`: codici che non possono essere rinumerati o mutati semanticamente senza approvazione architetturale.
- `NON_SUPPRESSIBLE_CODES`: codici di sicurezza che non possono essere silenziati inline.
- `PLUGIN_FORBIDDEN_EXITS`: i plugin non possono emettere Exit 2/3 (riservati alla semantica di sicurezza core).

:::tip[Deep-linking]
Ogni codice ha un'ancora permanente. Puoi collegarti direttamente a un codice specifico usando `https://zenzic.dev/it/docs/reference/finding-codes#z101`.
:::

## Panoramica delle Categorie

Zenzic organizza le rilevazioni in **sette categorie diagnostiche**, ognuna affrontando un pilastro specifico dell'integrità della documentazione:

| **Categoria** | **Range** | **Scopo** | **Severità Default** | **Sopprimibile?** |
|---|---|---|---|---|
| **Z0xx** | Migrazione e Compatibilità | Deprecazione engine; guida migrazione | `error` | ❌ No (abort fatale) |
| **Z1xx** | Integrità dei Link | Link rotti, vuoti, circolari; pagine orfane; problemi di percorso | `error`/`warning`/`info` | ✅ Sì |
| **Z2xx** | Sicurezza (credential scanner) | Rilevamento segreti; path traversal; incidenti di sicurezza | `warning`/`security_breach`/`security_incident` | 🔒 **Mai** |
| **Z3xx** | Integrità dei Riferimenti | Definizioni di riferimento dangling/duplicate | `error`/`warning` | ✅ Sì |
| **Z4xx** | Struttura | Directory index, pagine orfane, alt text mancante, asset di config | `info`/`warning` | ✅ Sì |
| **Z5xx** | Qualità Contenuti | Placeholder, contenuto corto, validazione snippet, regressioni | `warning`/`error` | ✅ Sì |
| **Z6xx** | Governance | Obsolescenza brand, parità traduzioni (opt-in) | `warning` | ✅ Sì |
| **Z9xx** | Engine e Sistema | Errori di esecuzione regole, timeout, diagnostiche di sistema | `error`/`warning` | ✅ Sì |

:::info[Sintassi di soppressione per-linea]
Sopprimi un finding su una linea specifica con un commento format-aware sulla stessa linea.\
**Markdown (.md):** `<!-- zenzic:ignore Zxxx -->`\
**MDX (.mdx):** `{/* zenzic:ignore Zxxx */}`\
Vedi la [Suppression Policy](./suppression-policy.mdx) per il riferimento completo, incluse le interazioni con la modalità `--strict`.
:::

### Exit Code Contract

Zenzic utilizza exit code per comunicare la severità attraverso le pipeline CI/CD:

* **Exit 0:** Tutti i check sono passati (o soppressi via `--exit-zero`).
* **Exit 1:** Errori e warning rilevati; usa `--strict` per promuovere i warning.
* **Exit 2:** Security breach (Z201 CREDENTIAL_SECRET) o violazioni di forbidden-term (Z204 FORBIDDEN_TERM). **Mai** soppressi.
* **Exit 3:** Incidenti di sicurezza rilevati (Z203 PATH_TRAVERSAL_FATAL). **Mai** soppressi, neppure con `--exit-zero`.

## Z0xx — Migrazione e Compatibilità

### Z000: UNSUPPORTED_ENGINE {#z000}

* **Severità:** `error` (Fatale — interrompe l'esecuzione immediatamente)
* **Contesto Tecnico:** Z000 è un **errore di configurazione fatale**, non un finding collezionabile. Emerge come eccezione `ConfigurationError` quando l'adapter factory incontra un alias di engine legacy deprecato o rimosso in `.zenzic.toml`. L'esecuzione si ferma prima che qualsiasi scansione inizi; Z000 **non** apparirà nell'output `--format json` né nell'array dei findings.
* **Rationale Architetturale:** Un alias di engine deprecato non causa semplicemente una misconfigurazione — invalida il determinismo della Virtual Site Map. La garanzia core di Zenzic è `score(repo) == score(repo)` in qualsiasi ambiente. Se l'adapter factory accettasse un engine sconosciuto e proseguisse con una euristica di fallback, la VSM prodotta sarebbe non-deterministica: ambienti diversi potrebbero risolvere adapter diversi, produrre route table diverse, e generare score diversi per input identici. L'abort hard è l'unica risposta che preserva il contratto di determinismo.
* **Rimedio:**
    1. Apri il tuo `.zenzic.toml` o `pyproject.toml`.
    2. Individua il campo `engine`.
    3. Imposta `engine = "standalone"`.
    4. Se stai usando MkDocs, assicurati che sia impostato `engine = "mkdocs"`.

## Z1xx — Integrità dei Link

### Z101: LINK_BROKEN {#z101}

:::info[Quality Score — Structural tier (30%) | −8.0 pts / occorrenza]
Z101 conta nel tier **Structural** del [Deterministic Quality Score](./scoring-algorithm.mdx). Penalità: **−8.0 pts per occorrenza**, capped a 30 pts per il tier.
:::

* **Severità:** `error`
* **Contesto Tecnico:** Emesso durante il Pass 2 (Validation) del Two-Pass Engine. Un link relativo punta a una risorsa che non esiste all'interno della **Virtual Site Map (VSM)**. Questo significa che, sebbene il file possa esistere fisicamente, è o fuori dallo scope di scansione dei docs o è stato escluso da una regola di esclusione.
* **Rationale Architetturale:** Un link rotto è la rottura silente di un contratto bidirezionale fra autore e lettore. L'autore ha committato un percorso; ogni lettore confida che quel percorso porti da qualche parte. Quando un file viene rinominato o cancellato, le pipeline CI standard non rilevano la rottura — il build ha successo, la test suite passa, e il danno si propaga in modo invisibile fino a quando un utente colpisce il 404. Zenzic intercetta questa rottura prima di qualsiasi build, divenendo l'unico gate nella pipeline capace di fermare questa classe di documentation rot alla sorgente.
* **Rimedio:**
    1. Verifica l'esistenza fisica del file di destinazione.
    2. Controlla il calcolo del percorso relativo (es. `../folder/target.md`).
    3. Assicurati che il file non sia matchato da `ignored_patterns` nella tua config.
    4. Se referenzi un file fuori da `docs/`, usa un percorso globale o un symlink (anche se relativo è preferibile).

<ZenzicOutput
  status="error"
  code="Z101"
  exitCode={1}
  compact
  rows={[{ code: 'Z101', file: 'docs/guides/setup.md:14', message: "Broken link → 'install.md' (target not found)", severity: 'error' }]}
/>

:::note[Confine Architetturale — Validazione di Frammenti Cross-Page]
Zenzic valida l’esistenza della **route** verso cui punta un link. Non valida il frammento specifico (`#intestazione`) all’interno di una pagina diversa. Se un link come `/docs/reference/cli#intestazione-specifica` punta a una route valida, Zenzic non emette alcun finding, anche se `#intestazione-specifica` non esiste in quella pagina.

Per gli anchor nella stessa pagina (link della forma `#sezione-in-questa-pagina`), vedere [Z102: ANCHOR_MISSING](#z102).

Per la validazione di frammenti cross-page — verificare che `#intestazione` esista all’interno di un’altra pagina — il generatore di siti statici (es. Docusaurus) esegue questo controllo in fase di build. Eseguire `npm run build` rivelerà gli anchor cross-page non validi che esulano dallo scope del route-graph di Zenzic.
:::

### Z102: ANCHOR_MISSING {#z102}

:::info[Quality Score — Structural tier (30%) | −5.0 pts / occorrenza]
Z102 conta nel tier **Structural** del [Deterministic Quality Score](./scoring-algorithm.mdx). Penalità: **−5.0 pts per occorrenza**, capped a 30 pts per il tier.
:::

* **Severità:** `error`
* **Contesto Tecnico:** Il file di destinazione è valido (Z101 passa), ma l'anchor HTML specifico (es. `#setup`) non si trova nel registro degli header del target. Zenzic effettua il parsing di tutti gli header Markdown e dei tag `<a id="...">` espliciti per costruire questo registro durante il Pass 1.
* **Rationale Architetturale:** Un heading è un contratto pubblico. Quando un autore scrive `## Setup` o dichiara `{#my-anchor}`, committa quell'identificatore a ogni link in entrata che lo referenzia. Quando il testo dell'heading viene modificato o l'ID esplicito rimosso, il contratto si rompe silenziosamente: il file esiste ancora (Z101 non scatta), ma la sezione che il lettore si aspettava non c'è più. Z102 enforcea la stabilità contrattuale a livello di anchor — che un check di esistenza file da solo non può fornire — intercettando le regressioni introdotte da ordinari rinomini di heading.
* **Rimedio:**
    1. Apri il file di destinazione e verifica il testo dell'heading.
    2. Assicurati che l'anchor combaci con la slugificazione engine-specifica (es. Docusaurus usa Kebab-case).
    3. Se usi ID custom, assicurati che la sintassi `{#id}` o `<a id="id"></a>` sia corretta.

### Z103: ORPHAN_LINK {#z103}

:::note[Quality Score — Nessun impatto DQS (0.0 pts)]
Z103 **non** riduce il [Deterministic Quality Score](./scoring-algorithm.mdx). Causa exit 0 in modalità standard, exit 1 con `--strict`. Vedi [Scoring Algorithm](./scoring-algorithm.mdx) per la tabella completa delle penalità.
:::

* **Severità:** `warning`
* **Contesto Tecnico:** Questo link punta a un file presente nella VSM ma non incluso nella struttura di navigazione del sito (sidebar/nav). Gli utenti possono collegarsi ad esso, ma non possono trovarlo tramite la UI.
* **Rationale Architetturale:** Una pagina orfana di navigazione esiste nel build ma non nel Knowledge Graph che i lettori percorrono. È raggiungibile solo via URL diretto — il lettore deve già conoscere l'URL per trovarla. Una pagina del genere ha discoverability zero: non può essere trovata seguendo alcun percorso di navigazione, voce di sidebar, o albero di documentazione. Z103 rende esplicita questa invisibilità, dando all'autore la scelta di o aggiungere la pagina alla navigazione (rendendola scopribile) o riconoscere intenzionalmente che è un endpoint nascosto.
* **Rimedio:**
    1. Aggiungi il file alla navigazione `mkdocs.yml` o al `sidebars.ts` di Docusaurus.
    2. Se la pagina è intenzionale (es. landing page nascosta), puoi sopprimere il warning con un commento `<!-- zenzic-disable Z103 -->`.

### Z104: FILE_NOT_FOUND {#z104}

:::info[Quality Score — Structural tier (30%) | −8.0 pts / occorrenza]
Z104 conta nel tier **Structural** del [Deterministic Quality Score](./scoring-algorithm.mdx). Penalità: **−8.0 pts per occorrenza**, capped a 30 pts per il tier.
:::

* **Severità:** `error`
* **Contesto Tecnico:** Un errore filesystem di basso livello. L'engine ha tentato di aprire un file referenziato da un link o asset ma ha ricevuto un `FileNotFoundError`. Questo si verifica tipicamente quando un file viene spostato o cancellato durante un processo di build concorrente.

  **Variante slug-mismatch (Docusaurus):** Z104 scatta anche quando un link assoluto punta a un prefisso di route project-owned (es. `/blog/`) scansionato da Zenzic, ma lo slug esatto non esiste nella Virtual Site Map. La causa più comune è un campo `slug:` nel frontmatter che differisce dall'URL usato in un link:

  ```mdx title="blog/2026-05-05-release-log.mdx"
  {/* Questo link è errato — lo slug reale è zenzic-v070-release */}
  [Read the previous post](/blog/zenzic-v070)
  ```

  ```yaml title="blog/2026-04-29-zenzic-v070-release.mdx (frontmatter)"
  slug: zenzic-v070-release
  ```

  Output Zenzic:

  ```
  blog/2026-05-05-release-log.mdx:12: '/blog/zenzic-v070' not found in the site map
  💡 Did you mean: '/blog/zenzic-v070-release/'?
  ```

  La Virtual Site Map viene costruita dagli slug nel frontmatter (non dai nomi di file fisici), quindi il file fisico `2026-04-29-zenzic-v070-release.mdx` non crea la route `/blog/zenzic-v070/` — solo `/blog/zenzic-v070-release/`.

* **Rationale Architetturale:** La variante slug-mismatch rivela una proprietà strutturale unica di Docusaurus: il campo frontmatter `slug:` disaccoppia l'URL pubblico di un file dal suo percorso fisico. Questo disaccoppiamento rende non-portabili i link URL-based — un link a `/blog/my-post/` può rompersi invisibilmente se lo `slug:` del file target viene cambiato, anche se il file stesso continua a esistere su disco e nessun Z101 scatta. La Virtual Site Map di Zenzic costruisce le route a partire dagli slug nel frontmatter, non dai nomi di file, rendendo rilevabile questa classe di rotture slug-mismatch silenziose prima che il build venga eseguito.
* **Rimedio:**
    1. Assicurati che nessun altro processo stia modificando la directory `docs/` durante la scansione Zenzic.
    2. Verifica che la tua impostazione `docs_dir` sia corretta e che il percorso del file sia assoluto rispetto alla root del repository.
    3. *(Variante slug-mismatch)* Esegui `zenzic inspect routes --kind physical` per vedere tutti gli URL canonici nella VSM, e aggiorna il link in modo che combaci con lo slug esatto dichiarato nel frontmatter del file di destinazione.

### Z105: ABSOLUTE_PATH {#z105}

:::info[Quality Score — Structural tier (30%) | −2.0 pts / occorrenza]
Z105 conta nel tier **Structural** del [Deterministic Quality Score](./scoring-algorithm.mdx). Penalità: **−2.0 pts per occorrenza**, capped a 30 pts per il tier.
:::

* **Severità:** `warning`
* **Contesto Tecnico:** I percorsi assoluti (es. `C:\Docs\page.md` o `/home/user/docs/page.md`) rompono la portabilità della documentazione. Zenzic li flagga per prevenire la sindrome "Funziona sulla mia macchina" nelle pipeline CI/CD.

  **I prefissi project-owned sono esenti da Z105 ma non da Z104.** I siti Docusaurus spesso usano link assoluti che iniziano con `/blog/`, `/docs/`, o altri valori di `routeBasePath` per attraversare i confini fra plugin. Zenzic auto-rileva questi prefissi dalla configurazione dell'engine (Zero-Config — nessuna entry richiesta in `.zenzic.toml`) e sopprime Z105 per essi.

  Tuttavia, sopprimere Z105 non significa che il link rimanga non controllato. Per i prefissi pienamente scansionati (es. `blog/` è in scope), Zenzic esegue un lookup in VSM e solleva un finding [Z104 — FILE_NOT_FOUND](#z104) se la route esatta è assente. Questo intercetta slug mismatch e post rinominati che rompono i link assoluti. Il costo del lookup è $O(1)$ — una singola `get()` su hash-map — senza impatto misurabile sul tempo di scansione.

  | Link | Z105 | Verifica VSM | Esito |
  | :--- | :---: | :---: | :--- |
  | `/blog/correct-slug` (slug presente in VSM) | ✅ esente | ✅ passa | Nessun finding |
  | `/blog/wrong-slug` (slug assente dalla VSM) | ✅ esente | ❌ fallisce | **Z104** |
  | `/developers/intro` (content root plugin sibling, pagina esiste) | ✅ esente | ✅ passa | Nessun finding |
  | `/developers/ghost` (content root plugin sibling, pagina assente) | ✅ esente | ❌ fallisce | **Z104** |
  | `/api/v1/users` (prefisso sconosciuto) | ❌ **Z105** | — | Z105 |

* **Rationale Architetturale:** Un percorso assoluto nella sorgente di documentazione vincola il link al layout filesystem di un singolo host — l'esatto opposto del contratto di portabilità che la documentazione deve onorare. A differenza del codice, dove gli import assoluti possono essere accettabili se scopati a un package pubblicato, un percorso assoluto in documentazione fa trapelare lo stato della macchina dell'autore in un artefatto pubblico: il build avrà successo sul laptop dell'autore e fallirà in CI, in un fork, o nell'ambiente di un contributor. Zenzic flagga Z105 come finding Structural perché la rottura non è stilistica — è un difetto di portabilità che si accumula silenziosamente: ogni percorso assoluto aggiunge un'altra assunzione environment-specific alla documentazione, fino a quando una riorganizzazione, un mirror, o una migrazione li fa emergere tutti insieme.
* **Rimedio:**
    1. Converti il link in un percorso relativo a partire dalla directory del file corrente.
    2. Usa `@site/` o alias engine-specifici simili se supportati (es. in Docusaurus).
    3. Se hai ricevuto un **Z104** (non Z105) su un link assoluto `/blog/` o `/docs/`, il prefisso di route è riconosciuto ma lo slug non esiste — vedi [Rimedio Z104](#z104) sopra.

### Z106: CIRCULAR_LINK {#z106}

:::note[Quality Score — Informativo | 0.0 pts (nessun impatto DQS)]
Z106 è puramente informativo e **non** riduce il [Deterministic Quality Score](./scoring-algorithm.mdx). Ispeziona con `--show-info`. Vedi [Scoring Algorithm](./scoring-algorithm.mdx#penalty-table) per il razionale dietro il design a penalità zero.
:::

* **Severità:** `info`
* **Contesto Tecnico:** Rilevato dal modulo Graph Integrity. Un insieme di link forma un ciclo diretto (A → B → A). È un segnale di telemetria strutturale: visibile via `--show-info`, escluso dallo scoring, e non blocca il Quality Gate.
* **Rimedio:**
    1. Rivedi il flow dei contenuti per vedere se un link può essere sostituito da una sezione "See Also" più ampia.
    2. Assicurati che gli utenti non rimangano intrappolati fra due pagine senza chiaro percorso di uscita.

:::note[Rationale architetturale]
**Knowledge Graph, non Dependency Graph.** Nel codice sorgente, un ciclo di dipendenze (modulo A importa B, che importa A) è un difetto di compilation-time. La documentazione è un Knowledge Graph: se un Tutorial collega una pagina Reference per dettagli tecnici, è atteso e desiderabile che la pagina Reference rimandi al Tutorial come esempio funzionante. Un grafo densamente interconnesso è segnale di UX di alta qualità, non un difetto.

**Score Anti-Pattern Prevention.** Elevare Z106 a Warning o Error dedurrebbe punti dal Quality Score, mettendo pressione agli ingegneri per rimuovere link utili al solo fine di soddisfare il linter. Questo viola il principio Zero-DBT: un linter deve flaggare solo difetti genuini. Un link circolare intenzionale non è un difetto da risolvere.

**AST Recursion Protection.** L'algoritmo di rilevamento cicli (DFS iterativa, Θ(V+E)) è un requisito meccanico del builder della Virtual Site Map. Identificare i cicli matematicamente è necessario per interrompere la ricorsione e prevenire loop infiniti durante la traversata del grafo — non è triggerato da una preoccupazione di qualità.

**Topological Telemetry.** `--show-info` espone i finding Z106 come metriche strutturali, non come violazioni. Una densità di cicli anomalmente alta su una singola pagina può indicare un problema di Information Architecture che vale la pena rivedere — ma quella valutazione spetta all'ingegnere, non allo static analyzer.
:::

### Z108: EMPTY_LINK_TEXT {#z108}

:::info[Quality Score — Structural tier (30%) | −1.0 pt / occorrenza]
Z108 conta nel tier **Structural** del [Deterministic Quality Score](./scoring-algorithm.mdx). Penalità: **−1.0 pt per occorrenza**, capped a 30 pts per il tier.
:::

* **Severità:** `error`
* **Contesto Tecnico:** Emesso quando il testo visibile in un link Markdown inline o in un reference link collassato è vuoto o composto da soli whitespace. Esempi: `[](./page.md)`, `[ ](./page.md)`, e `[][ref]`.
* **Rationale Architetturale:** Il testo del link è il contratto semantico machine-readable fra l'autore e ogni consumer downstream. Gli screen reader annunciano il testo del link come descrizione della destinazione di navigazione. I crawler dei motori di ricerca lo indicizzano come etichetta di relazione fra pagine. Chi naviga da tastiera vi si affida per capire dove il focus del Tab condurrà. Una label vuota o whitespace-only rompe tutti e tre i contratti simultaneamente: il link esiste nel DOM ma non comunica nulla. Zenzic classifica Z108 come finding Structural — non come preferenza di stile — perché degrada sia l'accessibilità sia il livello semantico del knowledge graph.
* **Rimedio:**
  1. Sostituisci la label vuota con testo descrittivo, es. `[Documentation](./page.md)`.
  2. Se il link è solo un placeholder, rimuovilo finché destinazione e label non saranno noti.
  3. Riesegui `zenzic check links` dopo l'edit per confermare che non rimangano finding Z108.

:::tip[Esempio eseguibile]
Per una dimostrazione pratica, vedi la [fixture z108-empty-link](https://github.com/PythonWoods/zenzic/tree/main/examples/rules/z108-empty-link) nel repository ufficiale degli esempi.
:::

### Z107: CIRCULAR_ANCHOR {#z107}

:::info[Quality Score — Structural tier (30%) | −1.0 pt / occorrenza]
Z107 conta nel tier **Structural** del [Deterministic Quality Score](./scoring-algorithm.mdx). Penalità: **−1.0 pt per occorrenza**, capped a 30 pts per il tier.
:::

<ZenzicOutput
  status="warning"
  code="Z107"
  exitCode={1}
  compact
  rows={[{
    code: "Z107",
    file: "docs/guide.md",
    line: 42,
    message: "Self-referential anchor link: anchor #intro points to a heading on this very page."
  }]}
/>

* **Severità:** `warning`
* **Contesto Tecnico:** Rilevato dalla `CircularAnchorRule` nel pluggable rule engine. Un link nella forma `[text](#anchor)` dove l'anchor si risolve in un heading della *stessa* pagina è logicamente circolare — naviga esattamente dove il lettore è già. La regola slugifica tutti gli heading nel file (lowercased, spazi in trattini, caratteri speciali rimossi) e li confronta con ogni link anchor locale.
* **Rationale Architetturale:** Un link nella forma `[text](#anchor)` dove `#anchor` si risolve in un heading nella stessa pagina è un ciclo degenere di lunghezza 1 — riconduce il lettore esattamente alla posizione che già occupa. È distinto da una legittima entry di table-of-contents in cima alla pagina (che linka in avanti verso un anchor più in basso). Z107 scatta solo quando il link e il suo heading risolto condividono lo stesso contesto di pagina: un self-loop che fornisce zero valore di navigazione e può confondere screen reader e chi naviga da tastiera che si aspettano che i link spostino il focus in una posizione diversa.
* **Rimedio:**
    1. Sostituisci `[text](#anchor)` con la prosa semplice `text` se non è intesa alcuna navigazione.
    2. Oppure linka al concetto in una pagina *diversa* che lo espande.
    3. Se il link è intenzionale (es. una entry di ToC in cima a una pagina lunga), per definizione non è circolare — rivedi il match dello slug dell'anchor.

## Z2xx — Sicurezza (credential scanner)

### Z201: CREDENTIAL_SECRET {#z201}

:::danger[Quality Score — Security Override | FATAL | Exit 2 | Non-suppressible]
Z201 triggera il Security Gate: il [Deterministic Quality Score](./scoring-algorithm.mdx) collassa a **0/100** incondizionatamente. Exit code **2** (credential leak) — bypassa `--exit-zero`. Una sorgente di documentazione che fa trapelare credenziali non può ricevere uno score di qualità. Vedi [Scoring Algorithm](./scoring-algorithm.mdx#security-override).
:::

:::danger[🔒 INVIOLABILE — Non può essere soppresso]
`zenzic:ignore: Z201` viene **silenziosamente rifiutato**. Il credential scanner scatta incondizionatamente su ogni linea. I finding di sicurezza sono fatti, non suggerimenti — un credential leak non può essere dichiarato un falso positivo.
:::

* **Severità:** `security_breach` (Exit 2)
* **Contesto Tecnico:** Il credential scanner analizza ogni linea — raw e normalizzata — per pattern di credenziali noti. La decodifica Base64 speculativa viene applicata ai token candidati: se la decodifica rivela un pattern di credenziale, la linea originale (codificata) viene flaggata. Questo previene l'offuscamento via Base64 encoding in valori di frontmatter o blocchi di codice.

Questo significa che i metadati Docusaurus (es. `` ```python title="file.py" showLineNumbers ``) sono pienamente supportati e mai flaggati.
* **Rationale Architetturale:** Un code block senza language tag è una regione opaca di testo dal punto di vista di ogni consumer downstream: i syntax highlighter non possono colorarla, la Snippet Guard (Z503) non può validarne la sintassi, gli screen reader la annunciano come testo preformattato indifferenziato, e gli indexer di ricerca non possono estrarne struttura semantica. Il tag mancante disabilita anche il gate stesso che intercetta gli esempi di codice rotti — un blocco senza tag è un blind spot per Z503. Zenzic classifica Z505 sotto Content perché l'omissione degrada silenziosamente il contratto che distingue la prosa di documentazione dal riferimento tecnico: un code block deve dichiarare che tipo di codice contiene, altrimenti lettori e tooling non possono fidarsene come esempio eseguibile.
* **Perché Zenzic implementa questo:** Check strutturale pure-Python che elimina la Node.js Tax dalla tua pipeline CI. Vedi [Zenzic vs. Proofreader](../explanation/structural-integrity.mdx#dimension-accessibility) per il razionale completo.
* **Rimedio:**
    1. Aggiungi un language tag immediatamente dopo i backtick di apertura: `` ```python ``, `` ```bash ``, `` ```toml ``.
    2. Per blocchi di solo output o display, usa `` ```text `` o `` ```plaintext ``.
    3. Per blocchi di tutorial che mostrano Markdown raw, usa `` ```markdown ``.

## Z9xx — Engine e Sistema

### Z901: RULE_ENGINE_ERROR {#z901}

:::warning[Non incluso nel Quality Score]
Z901 è un **errore a livello di sistema**. Non riduce il [Deterministic Quality Score](../explanation/health-metrics.mdx). Indaga il plugin o la regola che ha sollevato l'eccezione e segnala un bug se è uno scanner core.
:::

* **Severità:** `error`
* **Contesto Tecnico:** Un'eccezione non gestita si è verificata all'interno di una regola core o di un plugin. È un fallimento a livello di sistema che di solito indica un bug in Zenzic o un ambiente incompatibile.
* **Rationale Architetturale:** Il principio fail-visible di Zenzic richiede che ogni fallimento engine-internal emerga come finding osservabile, non come crash silente o risultato mancante. Un'eccezione non gestita in una regola o plugin che venga catturata e scartata produrrebbe un falso negativo: la scansione si completa con exit 0, ma finding che avrebbero dovuto essere emessi non lo sono stati. Il lettore e la pipeline CI vedono entrambi un risultato pulito — pulito solo perché l'analisi era incompleta. Z901 converte questo fallimento silente in un segnale esplicito e auditable: il risultato della scansione è ora noto come parziale, e la fonte dell'incompletezza è identificata e segnalabile.
* **Rimedio:**
    1. Controlla l'output CLI completo per un traceback Python.
    2. Segnala l'issue su `https://github.com/PythonWoods/zenzic/issues`.

### Z902: RULE_TIMEOUT {#z902}

:::warning[Non incluso nel Quality Score]
Z902 è un **timeout a livello di sistema**. Non riduce il [Deterministic Quality Score](../explanation/health-metrics.mdx). Semplifica il pattern regex della custom rule incriminata per risolverlo.
:::

* **Severità:** `error`
* **Contesto Tecnico:** Una regola ha impiegato troppo tempo per essere eseguita (default > 30s). È quasi sempre causato da un problema di **Catastrophic Backtracking** in una regular expression custom fornita in `[[custom_rules]]`.
* **Rationale Architetturale:** Un timeout di custom rule non è meramente un problema di performance — è una superficie di sicurezza. Un pattern regex con catastrophic backtracking (es. `(a+)+`) può essere triggerato da un file di documentazione craftato per bloccare l'intera scansione CI indefinitamente. È un attacco Regex Denial of Service (ReDoS) contro la pipeline di documentazione. Z902 è classificato come `error` (non `warning`) perché un timeout non rilevato può disabilitare silenziosamente un gate di sicurezza — il credential scanner e la privacy gate continuano a girare sui file successivi, ma la regola in timeout non emette finding. Permettere alla scansione di proseguire come se la regola fosse stata eseguita correttamente produrrebbe falsi negativi con exit 0.
* **Rimedio:**
    1. Rivedi i tuoi pattern regex custom in `.zenzic.toml`.
    2. Semplifica i pattern per evitare quantificatori annidati come `(a+)+`.
    3. Usa alternative non-backtracking se possibile.

### Z405: UNUSED_ASSET {#z405}

:::info[Quality Score — Governance tier (25%) | −3.0 pts / occorrenza]
Z405 conta nel tier **Governance** del [Deterministic Quality Score](./scoring-algorithm.mdx). Penalità: **−3.0 pts per occorrenza**, capped a 25 pts per il tier.
:::

* **Severità:** `warning`
* **Contesto Tecnico:** Un'immagine o file asset esiste nella directory ma non è mai referenziato da alcun file Markdown. Questi "Dark Assets" gonfiano il tuo repository e gli artefatti di build.
* **Rationale Architetturale:** Un asset non utilizzato è un nodo morto nel grafo di documentazione — un file che un tempo era referenziato da una pagina che è stata da allora cancellata, riorganizzata, o refactorizzata. Diversamente dal dead code sorgente (che compilatori e linter possono riportare), i dead asset in un repository di documentazione sono invisibili a tutti i check CI standard: il file esiste su disco, è committato, ed è incluso nell'artefatto di build. Col tempo, si accumulano: espandono la dimensione del repository, fanno crescere l'artefatto di build, ed estendono la superficie pubblicamente accessibile di file che nessun membro del team monitora attivamente. Zenzic classifica Z405 sotto Governance perché la proliferazione di asset è un sintomo di processo — il risultato di governance di refactoring incompleta — non un fallimento di authoring sui contenuti.
* **Rimedio:**
    1. Cancella il file inutilizzato.
    2. Oppure usalo in una pagina di documentazione dove appropriato.

### Z406: NAV_CONTRACT {#z406}

:::info[Quality Score — Governance tier (25%) | −2.0 pts / occorrenza]
Z406 conta nel tier **Governance** del [Deterministic Quality Score](./scoring-algorithm.mdx). Penalità: **−2.0 pts per occorrenza**, capped a 25 pts per il tier.
:::

* **Severità:** `error`
* **Contesto Tecnico:** Un conflitto fra la struttura fisica dei file e la config di navigazione dell'engine. Per esempio, una entry nav di `mkdocs.yml` che punta a `guide/setup.md` mentre il file è effettivamente in `guides/setup.md`.
* **Rationale Architetturale:** Il navigation contract è una promessa binaria: o il file è esattamente dove la config nav dice che sia, o l'engine di build produce un risultato indeterminato — una nav entry rotta, una pagina mancante, o un 404 silente. Diversamente da Z101 (un link in contenuto che punta a un file mancante), Z406 è un mismatch a livello di config: la navigazione dichiara una route che nessun file fisico attiva. Questa classe di rottura è particolarmente insidiosa perché sopravvive ai rinomini di file — quando un file si sposta senza un aggiornamento della config nav, il file fisico continua a esistere e la nav si costruisce comunque, ma la pagina è irraggiungibile dalla sidebar. Zenzic classifica Z406 sotto Governance perché le violazioni del nav contract sono il risultato di fallimenti di processo, non di errori di authoring sui contenuti.
* **Rimedio:**
    1. Allinea il percorso di navigazione nel tuo file di config con il percorso fisico del file.
    2. Esegui `zenzic check all` per verificare la fix attraverso la VSM.

### Z601: BRAND_OBSOLESCENCE {#z601}

:::info[Quality Score — Governance tier (25%) | −2.0 pts / occorrenza + Escalation]
Z601 conta nel tier **Governance** del [Deterministic Quality Score](./scoring-algorithm.mdx). Penalità: **−2.0 pts per occorrenza**, capped a 25 pts per il tier.

**Governance Escalation:** Oltre 10 occorrenze Z6xx totali, un moltiplicatore esponenziale si applica alla deduzione Governance: `deduction × 2^(excess / 5)`, capped al ceiling di 25 pts del tier. Venti finding Z601 (10 di eccesso) triggerano un moltiplicatore ×4 — quattro volte l'impatto governance baseline. Vedi [Scoring Algorithm — Governance Escalation](./scoring-algorithm.mdx#governance-escalation).

### Z602: I18N_PARITY {#z602}

:::info[Quality Score — Non incluso]
Z602 è un **check di integrità bilingue**. Non riduce il [Deterministic Quality Score](../explanation/health-metrics.mdx). Risolvilo per assicurare che il tuo contenuto tradotto sia completo e consistente.
:::

* **Severità:** `warning`
* **Contesto Tecnico:** Emesso dal modulo I18n Parity quando il mirror di traduzione di un file di documentazione in lingua base manca, o quando il frontmatter di un file tradotto diverge dalla versione canonica in lingua base. Vengono enforced due invarianti specifici:
    1. **Presenza del mirror:** Ogni file `.md` / `.mdx` nell'albero `docs/` base deve avere una controparte in ogni directory `i18n/<locale>/` configurata. Un mirror mancante significa che un locale serve silenziosamente il fallback non tradotto.
    2. **Parità del frontmatter:** Il frontmatter del file tradotto (almeno `sidebar_position`, `sidebar_label`, `title`) deve essere strutturalmente consistente con il file base. Una chiave stale o mancante significa che la sidebar del locale renderizza in modo errato.
* **Rationale Architetturale:** La Mirror Law (ADR-020) definisce un invariante strutturale: una traduzione non è un documento separato — è una trasformazione sintattica dello stesso documento. Quando il frontmatter di un file tradotto diverge dal canonico base (`sidebar_position` cambiato, `sidebar_label` mancante, `title` stale), la sidebar del locale renderizza un grafo di navigazione differente da quello della sidebar in lingua base. I due locale divengono architetturalmente asimmetrici: lettori in locale diversi sperimentano ordinamento di pagine differente, label di sezione differenti, e potenzialmente discoverability di pagine differente. Z602 enforcea l'invariante che la traduzione sia un'operazione di contenuto, non strutturale.
* **Rimedio:**
    1. Crea il file di traduzione mancante al percorso corrispondente sotto `i18n/<locale>/docusaurus-plugin-content-docs/current/`.
    2. Copia il blocco frontmatter in lingua base e traduci i valori — non aggiungere o rimuovere chiavi rispetto al base.
    3. Esegui di nuovo `zenzic check all` per confermare che la parità sia ripristinata.
    4. Per asimmetrie intenzionali (es. una pagina locale-only o una draft non ancora tradotta), sopprimi con `{/* zenzic:ignore: Z602 */}` sul blocco frontmatter o aggiungi il pattern di file a `i18n_exclude_patterns` in `.zenzic.toml`.

### Z111: VIRTUAL_ROUTE_BROKEN {#z111}

* **Severità:** `error` *(riservato)*
* **Contesto Tecnico:** Un link nella tua documentazione punta a un URL di virtual route
  (es., `/blog/tags/react/`) che **non è mai stato generato** perché nessun blog post porta
  quel valore di tag nel suo frontmatter `tags:`. La route non esiste nella VSM.

  È distinto da `Z101 LINK_BROKEN` (file fisico mancante): l'URL è
  strutturalmente valido per Docusaurus, ma nessuna sorgente di contenuto lo attiva. Zenzic costruisce
  la Virtual Route map a partire da `md_contents` (file già confermati esistenti su disco),
  quindi Z111 è strettamente un frontmatter/link mismatch — non un problema di cancellazione di file.

  Esempio: un file `docs/index.md` contiene `[React posts](/blog/tags/react/)`, ma nessun
  blog post in `blog/` ha `tags: [react]`. Docusaurus non renderizzerà mai quella pagina;
  il link è un 404.

* **Rimedio:**
    1. Identifica lo slug del tag nell'URL della route rotta (es., `react` da `/blog/tags/react/`).
    2. Cerca nella tua directory `blog/` post il cui frontmatter `tags:` dovrebbe includere
       quel tag — potrebbero usare una variante capitalizzata (`React`) o un sinonimo.
    3. O aggiungi il tag ai post rilevanti, o aggiorna il link per puntare a un tag
       effettivamente generato (es., `/blog/tags/reactjs/`).
    4. Se il link è forward-looking (un tag che intendi introdurre), sopprimi temporaneamente
       con `{/* zenzic:ignore: Z111 */}` sul link incriminato.

### Z113: AUTHOR_KEY_COLLISION {#z113}

* **Severità:** `error` *(riservato)*
* **Contesto Tecnico:** Due o più file `authors.yml` di Docusaurus (o `blog/authors/*.yml`)
  dichiarano la stessa author key. Docusaurus fonde queste definizioni deterministicamente
  per priorità, ma il risultato del merge è silente e fragile — una collisione di chiave crea una
  dipendenza nascosta di configurazione fra file che sono tipicamente mantenuti indipendentemente.
* **Rimedio:**
    1. Cerca l'author key in collisione in tutti i file `authors.yml` sotto `blog/`.
    2. Decidi quale definizione è canonica e rinomina la chiave duplicata.
    3. Aggiorna ogni blog post che usa la chiave rinominata nella sua lista `authors:`.

### Z114: LARGE_PAGINATION_SET {#z114}

* **Severità:** `info` *(riservato)*
* **Contesto Tecnico:** Il plugin blog genererebbe più di 200 pagine di indice paginato
  (`/blog/page/N/`). Zenzic fa emergere questo come finding informativo — non come errore

### Soppressione delle Diagnostiche

Zenzic supporta la **soppressione line-level, per-codice** via commenti inline. Aggiungi un commento `zenzic:ignore` alla fine di qualsiasi linea per silenziare una diagnostica specifica solo per quella linea.

**Soppressione format-aware (CEO-143 — Polymorphic Suppression Protocol):**

Per i file ``.md`` usa un commento HTML standard (invisibile nel Markdown renderizzato):

```markdown
The Obsidian era defined our foundations. <!-- zenzic:ignore: Z601 -->
```

Per i file ``.mdx`` usa un commento JSX (invisibile nell'MDX renderizzato, sicuro per Docusaurus/React):

```mdx
The Obsidian era defined our foundations. {/* zenzic:ignore: Z601 */}
```

Ogni commento di soppressione silenzia **solo** il codice specificato su quella linea. Per sopprimere codici multipli su una linea, aggiungi commenti multipli. Per esentare un intero file, usa `obsolete_names_exclude_patterns` in `.zenzic.toml` (Z601) o i pattern `excluded_files` rilevanti.

:::tip[Usa la soppressione con parsimonia]
La soppressione è per decisioni intenzionali e documentate — non per silenziare finding che non hai rivisto. Ogni linea soppressa dovrebbe avere un commento corrispondente o una entry ADR che spieghi il perché.
:::

### Workflow Raccomandato

1. **Baseline scan:** Esegui `zenzic check all` per stabilire una baseline di finding.
2. **Prioritizza la sicurezza:** Affronta tutti i finding Z2xx (credential scanner) immediatamente — sono security-critical.
3. **Fix di issue strutturali:** Risolvi i finding Z4xx (Structure) per assicurare navigazione e accessibilità corrette.
4. **Miglioramento qualità graduale:** Affronta i finding Z5xx (Content Quality) in modo incrementale come parte della normale manutenzione della documentazione.
5. **Sopprimi violazioni intenzionali:** Usa commenti inline con parsimonia per decisioni di design (es., landing page nascoste, sezioni sperimentali).

### Considerazioni Engine-Specifiche

* **Docusaurus:** I warning Z103 (ORPHAN_LINK) possono essere intenzionali per pagine fuori dalla sidebar principale. Considera di usare le route in `sidebars.js` o di sopprimere questi finding.
* **MkDocs:** Z401 (MISSING_DIRECTORY_INDEX) è particolarmente rilevante in doc gerarchiche; assicurati che ogni directory abbia un `index.md`.
* **Modalità Standalone:** La rilevazione orfani (Z103, Z402) è disabilitata senza un navigation contract. Usa esplicitamente.

## Integrazione con CI/CD {#cicd-integration}

Per la massima efficacia, integra i check Zenzic nella tua pipeline CI/CD:

```bash
# Fail on any error (Z1xx, Z4xx, Z9xx)
zenzic check all

# Fail on errors OR warnings (promote with --strict)
zenzic check all --strict

# Always exit 0 for non-blocking audits
zenzic check all --exit-zero
```

Usa configurazioni environment-specific per adattare la severità:

```toml
[zenzic]
engine = "docusaurus"
strict = false  # Warning only in dev; usa --strict in CI

[[rules]]
code = "Z502"
minimum_words = 50
```
